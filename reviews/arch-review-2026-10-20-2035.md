# Architecture Review — 2026-10-20

Scope: the most complex gameplay systems — settler tasks / choreography, logistics, construction,
unit demand (building workers, construction workers, garrison, recruit), inventory/piles, and the
composition root that wires them (`GameServices`, `FeatureRegistry`, `GameCore`). The renderer is
large but was left out on purpose: it is I/O, not simulation logic.

`docs/architecture/logistics-task-simplification.md` has already been applied (single numeric job id,
single `clearJobId` owner, `JobKind`, `UnitJobService`). This review does not repeat it. It looks at
what is still structurally hard after that work.

## System Overview

The simulation is a set of ~27 `FeatureDefinition`s loaded by `FeatureRegistry` in dependency order
on top of a kernel of `systems/` (movement, pathfinding, choreo runtime, inventory, recruit, scheduler,
reservation). `GameState` holds entities and occupancy. `EventBus` carries cross-feature notifications.
Unit behaviour all runs through **settler-tasks**: every unit has a `UnitRuntime`, and jobs are
`ChoreoJobState` node lists run by executors registered on a shared `ChoreoSystem`. Domain systems
(logistics, building-demand, construction-demand, garrison, barracks, recruit) are *dispatchers*: they
decide which unit should do what, push a synthetic choreo job through `TaskDispatcher.assignJob`, and
then react to `settler:taskCompleted/Failed`.

That shape is sound: a push-based dispatch model over a generic job runtime. Most of the complexity
comes from four things around it:
1. **Unit commitment** ("who owns this unit right now") is spread over ~10 places.
2. **Job ownership** is implicit: completion is broadcast, and synthetic jobs are rebuilt by hand on restore.
3. **settler-tasks** sits in the wrong layer. It depends on domain features, and it is split by line count rather than by responsibility.
4. **Initialization is two-phase without need.** That forces nullable, late-injected dependencies.

## Issues

### 1. Unit commitment state is fragmented across ~10 owners

**Impact:** "Is this unit free? Who is it working for?" has no single answer. Every feature that
commits units has to clean up its own state in three situations: entity removal, task failure and
save/restore. That is where ordering constraints come from (e.g. `UnitReservationRegistry` must
subscribe to `entity:removed` before `EntityCleanupRegistry`). It is also where "idle" means different
things to different callers, and where most restore bugs are likely to start.

**Current state.** A unit's commitment is described by all of these at once:

| Where | What it says |
|---|---|
| `entity.jobId` | busy flag (used by `IdleCarrierPool.isIdle`) |
| `UnitRuntime.state / job / moveTask` (`settler-tasks/unit-state-machine.ts`) | IDLE / WORKING / INTERRUPTED; `isWorking()` = `WORKING \|\| moveTask` |
| `UnitRuntime.homeAssignment` + `BuildingWorkerTracker` | assigned workplace |
| `UnitReservationRegistry` (`systems/unit-reservation.ts`) | "don't let the player move it", with a `purpose` string |
| `SettlerBuildingLocationManager` | inside / approaching a building (owns `entity.hidden`) |
| `TransportJobRecord.carrierId` | carrier committed to a transport |
| `ConstructionWorkerDemand.workerId` | digger/builder committed to a site |
| `BuildingDemand.committedUnitId` | specialist en route to a workplace |
| `TowerGarrisonManager` en-route map, `BarracksTrainingManager`, `UnitTransformer.pending` | garrison / training / recruitment |
| `CombatSystem.isInCombat` | consulted by the state machine to skip work |

Each dispatcher keeps its own `unit → thing` map and has to find its entry again on job events
(`UnitDemandJobHandlers.findByUnit` does a linear scan over all site demands in
`construction-site-demand.ts`).

**Recommended direction:** Give each unit one **commitment record**, owned by the unit runtime
(settler-tasks):
`{ owner: JobKind | 'player-move' | 'idle', ownerRef: number /* demand/record/tower id */, reserved: boolean }`.
- Unit reservation becomes a property of the commitment, not a separate registry. Player-move commands check `reserved`.
- `IdleCarrierPool`, `findIdleSpecialist`, the debug panel and diagnostics all read the same "idle" definition.
- Dispatchers look up *their* demand by `ownerRef` instead of keeping reverse `unit → demand` maps.
- Entity removal clears the commitment in one place, and the owner is told (see Issue 2).

Domain maps (`TransportJobStore`, garrison slots) can stay as the domain's own truth. They just stop
being the *only* way to know who owns a unit.

### 2. Job ownership is implicit: broadcast completion + hand-rebuilt synthetic jobs

**Impact:** Every dispatching feature has two code paths, a live one and a restore one. Every job
event goes to every listener, and each listener filters it. Adding a new dispatch-style job type means
touching events, filters, persistence exclusion and an `onRestoreComplete` rebuild.

**Current state:**
- `settler:taskCompleted / taskFailed` are subscribed by logistics, building-demand, construction-demand, tower-garrison (twice: manager + feature) and `UnitTransformer`. Each filters by `kind` and/or a pending map. `systems/unit-demand-loop.ts` exists only to standardise that filtering.
- `ChoreoJobState` (`systems/choreo/types.ts`) has become a grab-bag: `transportData`, `waypoints`, `metadata` ("replaces carryingGood hacks"), `onCancel` closure, `synthetic` flag.
- `synthetic` jobs are skipped by `settler-task-persistence.ts`. Each owner then rebuilds them by hand: `LogisticsDispatcher.restoreJobs()`; `TowerGarrisonFeature.onRestoreComplete` re-creates `WORKER_DISPATCH` choreos and re-reserves units; `ConstructionSystem` re-emits `construction:workerNeeded`; building-demand/barracks/victory use `forEachCompletedBuilding` to replay what `building:completed` did live.

**Recommended direction:** Add a **JobKind handler registry** on the job runtime, so every job has
exactly one owner it reports back to:
```
interface JobKindHandler<P> {
  build(params: P): ChoreoNode[];                 // deterministic: params → nodes
  onCompleted(unitId, params): void;
  onFailed(unitId, params, info): void;
  onUnitRemoved?(unitId, params): void;
}
```
- A job is plain data, `{ kind, params, nodeIndex, targets }`. Persistence stores it the same way for XML and synthetic jobs. On restore, `build(params)` regenerates the nodes. The `synthetic` exclusion and most hand-written `restore*` paths disappear.
- Completion goes straight to the owner. No broadcast filtering. `settler:task*` events stay only for timeline/debug.
- `onCancel` closures, `metadata` and `transportData` become the typed `params` of their kind.

This builds on Issue 1: `ownerRef` in the commitment record is the same thing as `params`' identity.

### 3. settler-tasks depends on domain features (inverted layer, half-finished plugin model)

**Impact:** settler-tasks is the job *runtime*, and in principle the lowest-level piece of unit
behaviour. In practice it is a hub that imports eight features. That prevents a clean dependency order.
It is why `construction-demand` has to be a separate `FeatureDefinition` loaded at tier 4. It is also
why domain knowledge leaks into generic executor contexts.

**Current state:**
- `SettlerTaskFeature.dependencies` lists building-construction, building-overlays, combat, production-control, material-transfer, work-areas, settler-location and inventory. It also imports ore-veins.
- `ConstructionSiteManager` is part of `InventoryExecutorContext` (`choreo-types.ts`) and `BuildingPositionResolver`. `ControlContext` has *optional* `executeCommand` / `inventoryManager` that only TRANSFORM_RECRUIT needs.
- `ChoreoSystem` is already a plugin registry: construction, recruit and transport register their own executors. But `registerCoreExecutors` still registers domain executors such as GET_GOOD/PUT_GOOD, RESOURCE_GATHERING, PRODUCE_VIRTUAL and HEAL.
- Executors read the current work handler from **mutable shared contexts**. `WorkerJobLifecycle.prepareNodeTick` assigns `movementCtx.entityHandler = …` before every node. That is hidden per-tick global state.

**Recommended direction:** Finish the inversion.
- The **core runtime** (settler-tasks) keeps only domain-free executors: movement, wait, visibility, animation, check-in. It depends on `systems/` plus settler-location.
- **Domain executors are registered by the feature that owns the domain**: inventory/production for goods nodes, construction for site nodes, combat for heal/attack. Construction, recruit and transport already work this way.
- Pass the work handler explicitly: resolve it into the job at start, or pass it as an executor argument. Do not mutate a shared context.
- After that, settler-tasks moves to tier 1, and construction-demand can join the construction feature.

### 4. settler-tasks is split by line count, not by responsibility

**Impact:** It is hard to say which class owns a unit's lifecycle. One operation passes through 3–5
objects. Duplicated logic drifts.

**Current state.** For example, `assignJob` with an active job runs:
`SettlerTaskSystem.assignJob → UnitJobService.assignJob → interruptJobForCleanup → WorkerTaskExecutor.interruptJob → WorkerJobLifecycle.interruptJob`.
- `worker-job-lifecycle.ts` says in its header that it was "moved out of WorkerTaskExecutor to keep that class under the max-lines limit".
- `WorkerTaskExecutor.completeJob/interruptJob` only delegate.
- The `UnitRuntime` factory exists twice (`SettlerTaskSystem.getOrCreateRuntime` and the `createRuntime` callback passed to `SettlerLifecycleCoordinator`, which also has its own `getOrCreateRuntime`).
- `IDLE_SEARCH_COOLDOWN` is defined in three files, and `buildAllSettlerConfigs()` is called twice.
- Idle cooldown uses two mechanisms: handle-tracked in `SettlerLifecycleCoordinator.scheduleIdleCooldown`, and untracked closures capturing `runtime` in `UnitStateMachine.handleIdle/handleWorking`.
- About 15 `SettlerTaskSystem` methods only forward to `BuildingWorkerTracker` (`assignWorkerToBuilding`, `getOccupantCount`, `findIdleSpecialist`, …).

**Recommended direction:** Split by concept, with each piece a peer export of the feature:
- **JobRunner**: owns `UnitRuntime`. It is the only place that runs start/advance/complete/interrupt and `entity.jobId`, and it is the `TaskDispatcher` implementation.
- **WorkerAutonomy**: idle search, work handlers, job selection, "return home and wait".
- **WorkerAssignments** (today's `BuildingWorkerTracker`): exported directly instead of through facade methods.
- **UnitVisualSync**: direction tracking, walk/idle animation.

`SettlerTaskSystem.tick` then becomes one loop that calls these. Each file stays under the size limit
because it has one job, not because code was cut out to fit.

### 5. Two-phase initialization causes nullable, late-injected dependencies

**Impact:** Nullable dependencies, `!` getters and setter injection go against the project's
optimistic-programming rule. They hide the real dependency graph from `FeatureDefinition.dependencies`.
They also add a "not ready yet" state that every consumer has to put up with.

**Current state:** `GameCore` builds `TerrainData` *before* `GameServices`, then hands it over right
away through `services.setTerrainData()` → `FeatureInstance.onTerrainReady`. Because of that phase:
- `pileRegistry: BuildingPileRegistry | null`, passed through `setPileRegistry` in `GameServices` step 6. settler-tasks reads it through `getPileRegistry()` and throws if it is null.
- `setOreVeinData` (settler-tasks, sign system, persistence), and `setTerritoryCheck` on both settler-tasks and recruit, are pushed *backwards* by territory/ore-veins. Territory imports settler-tasks and recruit in order to inject into them.
- `GameServices.territoryManager` / `oreVeinData` are getters with `!`.
- `ChoreoBuilder.withContext({ gameState, terrain })` is a static global.
- `GameState.movement!` is late-bound through `initMovement` and used in 43 places. That makes `GameState` a service locator for a system.

**Recommended direction:** Single-phase construction. Put `terrain`, `gameData` and static registries
(pile registry, work areas) into `FeatureContext` at `create()` time. Territory and ore-vein data then
become ordinary exports, and consumers list them in `dependencies` and pull them. The reverse setters
go away, and so does the `| null`. Pass movement to features as a kernel service, the same way as
`tickScheduler`, instead of hanging it off `GameState`. Effort is low: terrain already exists when
`GameServices` is built.

### 6. Construction worker bookkeeping has two sources of truth

**Impact:** A digger's commitment is recorded twice, and so is its tile reservation. The two copies
have to be kept in step on every assign, interrupt, removal and restore. The manager also talks to the
demand system *inside the same feature* through the global event bus.

**Current state:**
- `ConstructionSiteManager` keeps `terrain.slots.assigned`, `building.slots.assigned` and `terrain.reservedTiles` (`claimDiggerSlot`, `reserveUnleveledTile`, …).
- `ConstructionSiteDemandSystem` keeps `demand.workerId` and `demand.reservedTileIndex`, and calls the manager's claim/release to mirror them (`construction-site-demand.ts:247-576`).
- The manager emits `construction:workerNeeded`. `construction-demand-feature.ts` turns `role === 'digger'` into `onSiteRegistered` and `'builder'` into `onMaterialsDelivered`. On restore, the event is emitted again to rebuild demands.
- `findSiteNeedingDiggers/Builders` (pull-model leftovers) remain on the manager.

**Recommended direction:** Split ownership cleanly.
- `ConstructionSiteManager` = physical site state only: terrain leveling progress, material costs and consumption, build progress, pile layout.
- `ConstructionSiteDemandSystem` = the only owner of "which workers are on which site, and which tile each digger holds". With Issue 2, a digger's reserved tile is part of its job params.
- Phase changes become direct calls inside the feature (or one internal callback). The demand system rebuilds its demands from site state on restore, without replaying events.

### 7. Pile positions are resolved in many places although `PileSlot.position` already exists

**Impact:** Several components can disagree about where a pile is. Construction sites, storage
buildings and free piles each take a different code path in the executors.

**Current state:** `systems/inventory/pile-slot.ts` says it "merges … PilePositionResolver (position)
into one flat record" and has `position: Tile`. Position logic still lives in:
`BuildingPileRegistry` (XML), `features/inventory/PilePositionResolver`,
`systems/inventory/construction-pile-positions.ts`,
`ConstructionSite.pilePositions` + `getConstructionPilePosition(s)`,
`settler-tasks/BuildingPositionResolver.getSource/DestinationPilePosition` (re-derives from XML, then
falls back to the construction site, then to the storage slot), and logistics
`TransportPositionResolver`.

**Recommended direction:** Positions are decided once, when a slot is created: the XML registry and
construction layout are *inputs to slot creation*. Every runtime consumer (executors, logistics,
renderer) then asks inventory for "the slot for material M at building B" and reads `slot.position`.
`BuildingPositionResolver` shrinks to building-relative offsets and work areas.

### 8. `systems/` vs `features/` splits domain concepts across two trees

**Impact:** You cannot tell where a concept lives from its name. The rule "classify by dependency
direction" (design-rules 2.0) pushes domain logic into `systems/` whenever it happens to have no
feature imports. The concept then ends up split across two folders, with re-export barrels in between.

**Current state:**
- **inventory**: 2.5k lines in `systems/inventory/`, plus `features/inventory/` whose `index.ts` mostly re-exports `systems/inventory` and adds pile-position/free-pile pieces.
- **recruit**: `systems/recruit/` (1.3k lines: player queue, tool sources, transformer, which is clearly domain logic) plus `features/recruit/` (wiring and executors).
- **carriers**: `systems/carrier-registry.ts` and `systems/idle-carrier-pool.ts`, plus a 72-line `features/carriers/`.
- `systems/unit-demand-loop.ts` is a domain helper for two features.

**Recommended direction:** Keep `systems/` for engine-level, domain-free infrastructure: movement,
pathfinding, spatial indices, tick scheduler, choreo runtime, entity cleanup. Each domain concept
(inventory, recruit, carriers) becomes one feature module containing all its code. Enforce layering
with dependency-cruiser rules between modules, not between directories. Low-level features such as
inventory are allowed to be imported by other features; that is what `dependencies` is for.

### 9. Composition root is a service locator; commands mostly bypass features

**Impact:** Features are "self-registering" in theory, but most real wiring goes through central
bags of dependencies. Adding a command or a consumer means editing `GameServices` / `GameCore`.

**Current state:**
- `GameServices` re-exposes ~30 feature internals as public fields. Inventory and movement are built by hand outside the registry (`registerExports('inventory', …)`), with hand-picked persistence ordering (`after: ['constructionSites']`).
- Only 4 features (trees, crops, production-control, tower-garrison) declare `commands`. Everything else goes through `registerAllHandlers` in `GameCore.wireCommandHandlers`, which receives `settlerTaskSystem`, `constructionSiteManager`, `combatSystem`, `inventoryManager`, `recruitSystem`, `unitTransformer`, … in one bag.

**Recommended direction:** Move each command handler into the feature that owns the mutation; the
`FeatureInstance.commands` hook already exists. Make inventory and movement regular features or kernel
services. Reduce `GameServices` to a typed lookup (`getFeature<T>(id)`) for the UI and debug layers,
instead of copying every export into a field.

---

### 10. Tick order and cleanup order are implicit

**Impact:** Determinism and correctness depend on orderings nobody declared. Reordering the
`loadAll([...])` list, or adding a dependency, silently changes simulation order.

**Current state:**
- Tick order = registration order (tick scheduler and movement by hand first, then feature load order). The `systemGroup` labels ('Units', 'Logistics', 'Military') are used only for display.
- Removal order relies on `CLEANUP_PRIORITY` (EARLY/DEFAULT/LOGISTICS/LATE) plus a constructor-order rule for `UnitReservationRegistry`.

**Recommended direction:** Make the groups real **tick phases** with a declared order
(Scheduler → Movement → Units → Logistics → Buildings → Military → AI). Systems declare their phase,
and the order inside a phase doesn't matter or is explicit. Once Issue 1 removes the separate
reservation registry, removal ordering comes down to "runtime commitment first, domain stores next,
inventory last", stated in one place.

## Priority Matrix

| Issue | Severity | Effort | Recommendation |
|-------|----------|--------|----------------|
| 2. Implicit job ownership / synthetic restore | High | High | Add a JobKind handler registry; jobs are `{kind, params}` data rebuilt by `build(params)`; route completion directly |
| 1. Fragmented unit commitment | High | High | One commitment record per unit in the runtime; fold `UnitReservation` into it; dispatchers key by `ownerRef` |
| 5. Two-phase init / late injection | High | Low | Put terrain + game data into `FeatureContext` at create; delete setters, `\| null` and `!` getters |
| 3. settler-tasks depends on domain features | High | Med | Core runtime keeps generic executors; domains register their own; no mutable shared executor contexts |
| 6. Construction worker double bookkeeping | Med | Low | Demand system owns workers + tile reservations; site manager owns physical state; drop internal events |
| 4. settler-tasks split by line count | Med | Med | Reorganise into JobRunner / WorkerAutonomy / WorkerAssignments / VisualSync; drop forwarders and duplicates |
| 7. Pile positions resolved in many places | Med | Med | Fix position at slot creation; every consumer reads `slot.position` |
| 8. systems/ vs features/ split by dependency | Med | Low | `systems/` = engine only; inventory, recruit, carriers each one module; enforce with dependency-cruiser |
| 9. Service-locator composition root | Low | Med | Move command handlers into features; shrink `GameServices` to a typed lookup |
| 10. Implicit tick/cleanup order | Low | Low | Turn `systemGroup` into declared tick phases; state cleanup order once |

**Suggested sequencing:** Do 5 first (cheap, and it untangles the dependency graph). Then 6 and 8
(local, low risk). Then 3 → 4, which settle what settler-tasks is. Do 1 + 2 together last: they are
the real simplification and are much easier once settler-tasks has a clear JobRunner to hang them on.
